# Module: ticket assignment

Accumulated facts about how this repo decides *who* a ticket is assigned to. Never frozen; append a dated section per ticket that changes this area. Every statement below carries `path:line` + commit sha on `main` — verify the line is still there and still says this before trusting it; if it doesn't, treat it as "not covered" and say so, don't silently carry it forward.

## PRD-20620 · 2026-10-21

- Before this ticket, `autotask_create_ticket`/`autotask_update_ticket` took `assignedResourceID` as a plain caller-supplied number with no coordination across calls (`src/handlers/tool.definitions.ts:553,664` @ `851f6bd`). Concurrent or rapid-succession calls from the same agent turn reliably collapsed onto one technician, since the LLM has no way to serialize its own tool calls against itself.
- `autotask_assign_least_loaded_resource` (`src/handlers/tool.handler.ts`, dispatch entry added at `2601250`) is the first code in this repo that queries `ResourceRoles` in the queue → resources direction. The resource → roles direction (`searchResourceRoles`, `src/services/autotask.service.ts:947` @ `851f6bd`) already existed; the reverse had never been needed before. Both directions read the same `ResourceRoles` entity, which carries `queueID` directly on each (resource, role, queue) assignment row (`src/types/autotask.ts:739` @ `851f6bd`).
- "Open" ticket, for counting purposes, means `status != 5` (Complete) — the same convention `searchTickets` already uses (`src/services/autotask.service.ts:476` @ `851f6bd`). If this repo ever adds more terminal statuses, `countOpenTicketsByQueueAndResource` (`src/services/autotask.service.ts`, added at `2601250`) needs to stay in sync with that definition, or the two tools will disagree about what counts as open.
- **The serialization lock is in-process only** (`src/utils/queue-lock.ts`, added at `2601250`). It prevents races between concurrent calls handled by the *same* server process; it does **not** prevent races if this server is ever deployed as multiple replicas against the same Autotask tenant. `docker-compose.yml` shows a single service with no replica count as of `2601250` — if that ever changes, this lock stops being sufficient and the next ticket touching this needs a shared lock (DB advisory lock or Redis) instead, not a bigger in-process one.
- A ticket created through this tool must have its `queueID` set explicitly in the create payload — there's no other way for a brand-new ticket to end up in the queue its assignee's eligibility was checked against. An existing ticket reassigned via the `ticketID` path is assumed to already be in that queue and is not re-stamped.

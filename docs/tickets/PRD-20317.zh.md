## 需求理解

一句话：给 Autotask MCP 工具 `autotask_search_contacts` 加上返回联系人自定义字段的能力，让下游流程能直接从同一个响应里拿到这些值，不用再多一次查询。

提单人（Felix.Zhou@mspbots.ai，2026-10-12 提交）希望 `autotask_search_contacts` 在返回匹配到的联系人时，把 Autotask 的自定义字段（user-defined fields）一并带在同一个工具响应里，这样调用方不需要额外的后续查询就能拿到这些值。需求明确限定在这一个工具的响应结构上——不涉及对 Autotask 联系人工具链的更大范围重构。目前没有可用的绕行方案。提单人对「方案预览」确认为「照原样」（见工单 `text_content` 的 Solution Preview 一节）。

## 现状（每条陈述均带 path:line）

本单的 Code Project 为空。工单原文里没有能唯一定位仓库的字符串，于是用 `autotask_search_contacts` 这个工具名本身去探测 `Code Project` 字段当前所有可解析的仓库——除一个尚未注册为字段选项的仓库外（见「阻塞」一节），其余全部零命中。那个仓库是 `https://github.com/MSPbotsAI/autotask-mcp`（检出于 `main` / `9700dde`），是一个封装 Autotask REST API 的 MCP 服务器，和 `chargebee-mcp`、`bamboohr-mcp`、`halopsa-mcp` 等一批已经是 `Code Project` 选项的「每家供应商一个 `*-mcp` 仓库」属于同一类。

在这个仓库内部：

- `autotask_search_contacts` 定义在 `src/handlers/tool.definitions.ts:311-331`。它的 `inputSchema` 只有 `searchTerm`、`companyID`、`isActive`、`page`、`pageSize`——没有任何字段选择类参数。
- handler（`src/handlers/tool.handler.ts:889-891`）直接调用 `s.searchContacts(a)`，把原始参数对象原样透传，没有做任何过滤。
- `searchContacts()`（`src/services/autotask.service.ts:328-358`）组装 Autotask 过滤条件后调用 `http.query<AutotaskContact>('Contacts', filters, { maxRecords: pageSize })`——从未设置 `opts.includeFields`。Autotask REST 查询只有在请求的 `IncludeFields` 里显式列出 `userDefinedFields` 时才会返回它（`src/services/autotask-http.ts:390-404` 的 `IncludeFields` 透传逻辑）。既然 `searchContacts()` 从未请求它，Autotask 就不会返回它——这一步和后面任何处理都无关，是独立的第一道闸。
- 即便 Autotask 返回了，compact 响应格式化器也会把它丢掉：`SUMMARY_FIELDS.contacts`（`src/utils/response.formatter.ts:27`）是一张硬编码白名单 `['id', 'firstName', 'lastName', 'emailAddress', 'companyID']`，`pickSummaryFields()`（`src/utils/response.formatter.ts:34-55`）只会把这几个字段拷到响应条目上（`autotask_search_contacts` 在 `COMPACT_SEARCH_TOOLS` 里，`src/utils/response.formatter.ts:117`）。这是两道互相独立的闸，不是一道。
- 这不是联系人专属的疏漏，而是一条有记录的、全平台性的既有决定。`CHANGELOG.md:661`（`[1.0.4]` 条目）记录了把 `userDefinedFields` 从工单搜索响应里删掉，就是为了解决「result exceeds maximum length」报错。这里的修复必须做成按需开启，而不是默认恢复到被这条决定推翻之前的行为。
- `AutotaskContact`（`src/types/autotask.ts:23-33`）的类型定义里没有 `userDefinedFields` 字段，不像 `AutotaskTicket`（`src/types/autotask.ts:67`：`userDefinedFields?: AutotaskUserDefinedField[]`）——这只是类型层面的缺口；索引签名 `[key: string]: any` 使它在运行时不构成阻碍。
- 这个实体上已经存在读写不对称：`autotask_update_contact` **已经**支持接收并透传 `userDefinedFields`（`{name, value}[]`），见 `CHANGELOG.md:95`——"the handler already forwarded all args, so only the schema needed the addition"。只有搜索/读取这条路径还缺这张单要的能力。
- `searchContacts()` 的参数类型是 `AutotaskQueryOptions`（`src/types/autotask.ts:671-680`），没有 `includeFields`。其它大多数搜索方法（`searchTickets`、`searchCompanies` 等 20 余个，见 `src/services/autotask.service.ts`）已经在用更丰富的 `AutotaskQueryOptionsExtended`（`src/types/autotask.ts:683-698`），它**确实**声明了 `includeFields?: string[]`——但目前 `tool.definitions.ts` 里没有任何实体把 `includeFields` 暴露成 MCP 侧参数，所以并不存在一条「调用方传字段列表、一路打到 Autotask」的现成实现可抄。这会是一条新的打通路径，不是照抄已有的。
- 通用的 compact 响应处理点（`src/handlers/tool.handler.ts:1677-1684`）在调用 `formatCompactResponse(result, entityType, { page, pageSize })` 时，`args` 本来就在作用域内——也就是说，调用方传的一个标志位，在当前「把自定义字段又剥掉」的那唯一一处，是可以拿到的。

wiki：本单未查阅 wiki 作为证据来源——`autotask-mcp` 是内部 MCP 工具服务器，不是 `MSPbotsAI/mbagent-wiki` 的 `ProductDocs/**`（记录 agent.mspbots.ai 界面行为）所覆盖的用户可见产品面。`mbp.py wiki find autotask` / `mbp.py wiki find custom field` 在 2026-10-12 同步后的 wiki 上均无相关小节；按 S2b 要求在此明示，而非静默跳过。

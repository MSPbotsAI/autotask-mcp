## Requirement understanding

One line: When the agent assigns multiple tickets to technicians at the same time, the tickets all end up with one person instead of being spread evenly across everyone.

The reporter (Carl Zhang, 2026-10-15) observes that when a queue has several eligible technicians ("multiple technicians at each level") and the agent processes several tickets in quick succession, every ticket lands on the same technician instead of being spread across the group. A follow-up comment from Jason Zhou (2026-10-20) proposes the root-cause fix directly: stop asking the LLM to decide who gets each ticket, and instead add a deterministic, lock-protected tool — `assign_least_loaded_tech(ticketId, queue)` — to "the existing AutoTask MCP service," so that concurrent ticket assignments serialize through one "pick the least-loaded resource" decision instead of N independent model guesses. This ticket has no Code Project set; S0b identified `autotask-mcp` as the target repo (see the `[CODE PROJECT BACKFILL]` comment on the ticket for the evidence).

## Current state (every claim carries path:line)

- The only resource-lookup tool is `autotask_search_resources` (`tool.definitions.ts:1170`), which returns name/email/active-flag — no open-ticket counts, no queue membership.

## Product design

### Goals / Non-goals

Goals:
- When the agent assigns tickets to technicians (create or reassign) and several assignments happen close together, ticket load should end up roughly even across the technicians eligible for that ticket's queue — not clustered on whichever technician the model named first.
- The fix must hold when assignment calls arrive **concurrently** ("multiple orders simultaneously"), not only when they happen to be processed strictly one after another.

Non-goals:
- Not redesigning Autotask's queue/role model, nor changing who is eligible to serve a queue.
- Not implementing skill-based or priority-weighted routing — "even" is defined by current open-ticket count, not ticket complexity.
- Not covering tickets a human assigns manually in the Autotask UI — this only governs assignments the agent makes through this MCP server.
- Not guaranteeing even distribution across multiple *replicas* of this server process — see Tech design "Non-functional" and the deployment-topology Open question below.

### Acceptance criteria AC1..ACn

- **AC1**: Given a queue with 2 or more active eligible technicians and no pre-existing backlog, when the agent assigns N tickets through the new flow within a short window (including concurrently), then the resulting ticket counts per technician differ by at most 1 (e.g. 10 tickets over 5 technicians → 2 each, not 10-on-one).
- **AC2**: Given a queue with exactly 1 active eligible technician, when tickets are assigned, then they all go to that technician and the flow neither blocks nor errors.
- **AC3**: Given technicians already carry uneven open-ticket counts before a new ticket arrives, when that ticket is assigned, then it goes to whichever eligible technician currently has the fewest open tickets in that queue (ties broken deterministically).
- **AC4**: Given two assignment calls are issued at effectively the same instant (the agent processing multiple tickets simultaneously), when both complete, then they must not both have acted on the same "who has the fewest tickets" snapshot — the second call's decision must reflect the first call's result, not a stale count.
- **AC5**: Given a queue currently has no active eligible technician, when the agent tries to assign a ticket there, then the tool reports this as a distinct, actionable error rather than silently assigning an inactive resource or surfacing an unrelated Autotask error.

### Open questions

- [已假设 / assumed] "Evenly distributed" is read as "by current open-ticket count per queue," not by complexity- or time-weighted load, and not skill-matched routing. If the business actually wants skill-based routing, AC1/AC3 and the selection logic in Tech design change — flagged for groom to confirm.
- [已假设 / assumed] "Multiple technicians at each level" is read as "multiple active technicians serving the same Autotask queue" — queue is the only grouping boundary this codebase already has data for (Autotask's `ResourceRoles` records resource + role + department/queue, `autotask.service.ts:966-969`). Neither the ticket nor Jason Zhou's comment defines "level" explicitly; if it means something else (a role tier, a priority tier), the eligibility query in Tech design §Change list needs to change.
- [不阻塞 / non-blocking] Whether PTO/out-of-office status (beyond the `isActive` flag Autotask already exposes) should also exclude a technician from "eligible" is not modeled anywhere this repo's code touches — defaulting to `isActive`-only until told otherwise.
- [不阻塞 / non-blocking] This repo's `docker-compose.yml` shows a single service with no replica count, consistent with one Autotask-tenant-scoped instance. If ops ever runs more than one replica of this server against the same Autotask tenant, the in-process lock in Tech design stops being sufficient and a shared lock (DB advisory lock / Redis) would be needed — flagged as a risk, not solved here, since there is no evidence from this repo alone that it applies.

## Tech design

### Conclusion

Add one new MCP tool, `autotask_assign_least_loaded_resource`, to this repo. It resolves the eligible-technician set for a ticket's queue, counts each one's current open tickets in that queue, assigns the ticket to whichever has the fewest (ties broken by lowest `resourceID`), and runs the whole read-then-write sequence inside an in-process async lock keyed by `queueID`, so calls arriving "at the same time" serialize instead of racing on the same stale counts. This follows Jason Zhou's 2026-10-20 proposal directly (an atomic tool, not an agent-side convention) and reuses this repo's existing ticket/resource query plumbing — no new external dependency, no schema change to existing tools.

### Where the current implementation lives

- Ticket create/update entry points to extend: `tool.definitions.ts:553,664`, `tool.handler.ts:917-929`, `autotask.service.ts:579,592`.
- Role-resolution helper to reuse as-is: `tool.handler.ts:846` (`fillAssignedResourceRole`) + `autotask.service.ts:1003` (`resolveRoleForResource`) — the new tool still needs a role ID for whichever resource it picks; it should call this helper rather than duplicate role logic.
- Resource/role listing to extend: `autotask.service.ts:947` (`searchResourceRoles`) is per-resource only; there is no per-queue reverse lookup yet (new code needed, see Change list item 1).
- Ticket counting to reuse: `autotask.service.ts:464` (`searchTickets`) already accepts arbitrary `QueryFilter[]`s (the same `assignedResourceID`/other filters used at `tool.handler.ts:900-913`); the new tool can reuse this with a `queueID` filter + `assignedResourceID in (...)` + an open-status filter — no new query primitive needed for counting itself.
- No prior art for "enumerate candidates, then act" exists in this repo (confirmed zero hits for "least loaded" / "round robin" / "load balanc(e/ing)" across `CHANGELOG.md` and `src/`) — the mutex pattern below is new to this codebase, not modeled on an existing convention.

### Data & API contract

New tool: `autotask_assign_least_loaded_resource`

Request (exactly one of `ticketID` / `createTicket` must be given):

```json
{
  "queueID": 29682901,
  "ticketID": 123456,
  "createTicket": null,
  "roleName": "Help Desk"
}
```

or, to create-and-assign in one call:

```json
{
  "queueID": 29682901,
  "ticketID": null,
  "createTicket": { "companyID": 29683561, "title": "..." },
  "roleName": null
}
```

(`createTicket` takes the same shape `autotask_create_ticket` already accepts, minus `assignedResourceID` — that field is computed, not supplied.)

Response:

```json
{
  "result": {
    "ticketID": 123456,
    "assignedResourceID": 207,
    "assignedResourceRoleID": 44,
    "consideredResources": [
      { "resourceID": 207, "openTicketCount": 3 },
      { "resourceID": 311, "openTicketCount": 3 },
      { "resourceID": 455, "openTicketCount": 7 }
    ]
  },
  "message": "Assigned ticket 123456 to resource 207 (3 open tickets in queue 29682901, lowest among 3 eligible)"
}
```

Errors: `queueID` with zero active eligible resources raises a distinct `NoEligibleResourceError` naming the queue — not a generic Autotask error (AC5).

Backward compatibility: purely additive. `autotask_create_ticket` (`:553`) / `autotask_update_ticket` (`:664`) are unchanged — an agent that wants to name a specific technician explicitly still can; this is a new, optional tool alongside them, not a replacement.

### Key flow / sequence

```
Agent -> autotask_assign_least_loaded_resource(queueID, ticketID | createTicket)
  tool.handler.ts: queueLock.run(queueID, async () => {
    1. resources = autotaskService.getEligibleResourcesForQueue(queueID)
       -> if resources.length === 0: throw NoEligibleResourceError(queueID)
    2. counts = autotaskService.countOpenTicketsByQueueAndResource(queueID, resources.map(r => r.resourceID))
    3. chosen = resource with min(counts), tie-break by lowest resourceID
    4. fillAssignedResourceRole(payload, roleName)   // existing helper, tool.handler.ts:846
    5. if ticketID: autotaskService.updateTicket(ticketID, { assignedResourceID: chosen, ... })
       else:        autotaskService.createTicket({ ...createTicket, assignedResourceID: chosen, ... })
  })
  <- result includes the chosen resourceID and the counts considered, for auditability
```

Because steps 1-5 run inside a single `queueLock.run(queueID, ...)`, a second call for the same `queueID` arriving while the first is still between steps 1 and 5 waits until the first finishes, then re-reads counts and sees the first ticket already counted. This is the mechanism that satisfies AC4.

### Non-functional

- **Idempotency & concurrency**: the queue-scoped async lock (`queue-lock.ts`) serializes same-queue calls within one Node process — the only failure mode this change closes. Different queues proceed in parallel; there is no unnecessary cross-queue serialization.
- **Performance**: counting is one `searchTickets` query bounded by the eligible-resource count (typically a handful of technicians per queue). No caching is added; no new hot path is expected at normal MSP ticket volumes. No numeric SLA was requested in the ticket, so none is invented here — if one exists it belongs in groom.
- **Security**: no new auth surface. This tool runs under the same Autotask credentials (`AUTOTASK_USERNAME`/`AUTOTASK_SECRET`, `docker-compose.yml`) as every other tool in this server — no new secret, no new scope.
- **Multi-tenant isolation**: this MCP server is already scoped to one Autotask tenant per deployed instance (one credential set per `.env`/`docker-compose.yml`). This change introduces no cross-tenant surface, and that existing isolation boundary is unchanged. There is no further "tenant" dimension inside this codebase to isolate — see the Test cases note on why the usual multi-tenant test line is handled differently here.
- **Observability**: log the full decision (queueID, each candidate's count, the chosen resourceID) at `info` via the existing `this.logger` (matching existing call sites, e.g. `:584` in `createTicket`), so a questionable pick is auditable after the fact.

### Implementation notes / deviations from the tech design

- **Fixed a gap the design's own flow sketch had**: the `createTicket` path never set the new ticket's `queueID`, since the Data & API contract's `createTicket` shape (deliberately) omits it — it only has the top-level `queueID` used to pick the technician. Without explicitly carrying that into the ticket payload, a newly created ticket would have no queue at all. Fixed by setting `payload.queueID = queueID` only on the create path (an existing ticket on the `ticketID` path is assumed to already be in that queue, since that is the queue its eligibility was checked against).
- `getEligibleResourcesForQueue` follows `searchResourceRoles`'s existing precedent of treating `ResourceRoles.isActive` as "active assignment" without a second join to `Resources.isActive` — consistent with how `resolveRoleForResource` already works, not a new convention.
- Added a defensive validation guard (exactly one of `ticketID`/`createTicket`) beyond what the ACs require (TC-DEV1); this is a safety net a caller could trip over, not a scope change.

> 工具内部在一把锁里依次完成：查各技术人员单量 → 加上"已分出但 Autotask 可能还没反映"的预留数 → 选出单量最少的人 → 写入 Autotask 并记录预留 → 释放锁。锁可以用数据库行锁或 advisory lock，按租户 + 队列加锁。
> agent 只负责判断这张单子该不该分、分到哪个队列，然后调用这个工具。
> 10 张单子同时进来，在工具层会被排成串行处理，每张都能看到前一张的分配结果，自然就是轮流分给单量最少的人。

## 需求理解

一句话：agent 同时给多个技术人员分配工单时，单子全都分给了同一个人，而不是均匀分给大家。

提单人（Carl Zhang，2026-10-15）观察到：当一个队列里有多名符合条件的技术人员（"每个 level 的多个技术人员"），agent 短时间内连续处理多张工单时，所有工单都落到了同一个技术人员身上，而不是分散到这个群体里。Jason Zhou 的后续评论（2026-10-20）直接给出了根治思路：不要再让 LLM 自己决定每张单给谁，而是加一个确定性的、带锁的工具——`assign_least_loaded_tech(ticketId, queue)`——放进"已存在的 AutoTask MCP 服务"里，让并发的工单分配都串行走同一个"挑单量最少的人"的判定，而不是 N 次互相看不见的模型猜测。本单 Code Project 原为空；S0b 已定位到目标仓库 `autotask-mcp`（依据见工单上的 `[CODE PROJECT BACKFILL]` comment）。

## 现状（每条陈述都带 path:line）

- `src/handlers/tool.definitions.ts:553`（`autotask_create_ticket`）与 `:664`（`autotask_update_ticket`）把 `assignedResourceID` 当作调用方直接传入的普通数字，schema 里没有任何约束或提示。
- `src/handlers/tool.handler.ts:917-929` 把两个工具都直接转给 `buildTicketPayload(...)` 和 `autotaskService.createTicket` / `updateTicket`（`src/services/autotask.service.ts:579`、`:592`），而这两个方法本身就是对 Autotask `Tickets` 实体的直通调用（`http.create('Tickets', ticket)` / `http.update('Tickets', id, updates)`）。这条路径上没有任何计数、选人或加锁逻辑。
- `src/handlers/tool.handler.ts:846`（`fillAssignedResourceRole`）只负责给**已经选定**的资源补齐角色（经由 `autotaskService.resolveRoleForResource`，`src/services/autotask.service.ts:1003`）——它从不决定**该选哪个**资源。
- 唯一的资源查询工具是 `autotask_search_resources`（`tool.definitions.ts:1170`），返回姓名/邮箱/是否在职——没有当前单量，也没有队列归属信息。
- `autotask_search_resource_roles`（`tool.definitions.ts:931`，service 层 `src/services/autotask.service.ts:947`）回答的是"资源 X 持有哪些角色"（一行对应一个角色，是从 Autotask 原本"资源+角色+部门/队列"一行一条的形状折叠出来的，见 `autotask.service.ts:966-969` 的注释）。反方向的查询——"哪些在职资源服务队列 Q"——目前完全不存在，所以这个代码库现在没有任何办法枚举出一个队列的候选技术人员集合。
- `autotask_list_queues`（`tool.definitions.ts:2620`）只列队列 ID，不带其下资源。
- `package.json` 里没有 Redis、数据库或任何其它共享状态依赖——这个服务按现状是无状态的，每次请求独立处理。
- 综合结果：**谁拿到这张单**完全由调用方的 LLM 在调 `autotask_create_ticket` / `autotask_update_ticket` 那一刻决定。本仓库里没有任何机制在并发调用之间协调这个决定——这正好对应被报告的缺陷：做决定的是 agent，不是这个服务，而且它看不到"一秒前刚分出去一张给谁了"。
- `CHANGELOG.md` 与 `src/` 里搜 "least loaded"、"round robin"、"load balanc(e/ing)" 零命中——这是本仓库的新地盘，不是哪个曾经好用的东西退化了。

wiki：未覆盖。`mbp.py wiki find` 对 "autotask ticket assign"、"ticket routing technician"、"resource assignment queue"、"AI Ticket Triage" 均无命中。唯一沾边的一条是 `ProductDocs/11-SOP-Agents.md § The connector tool list is loaded dynamically, per agent`（_verified_ 2026-09-17，v20260917.1030），它证实了 agent 确实通过网关实时调用 Autotask MCP 的工具（demo 租户在 v4.1.517 时数出 98 个工具），但完全没提分配公平性。如实记录这个缺口，不跳过。

## 产品设计

### 目标 / 非目标

目标：
- agent 给技术人员分配工单（新建或改派）时，如果多次分配发生在相近时间，最终单量应该在该工单队列的候选技术人员之间大致均衡——而不是扎堆在模型第一个想到的那个人身上。
- 这个修复在分配调用**并发**到达时（"同时处理多个订单"）也要成立，不能只在恰好被严格顺序处理时才成立。

非目标：
- 不重新设计 Autotask 的队列/角色模型，也不改变谁有资格服务某个队列。
- 不实现按技能或按优先级加权的路由——"均衡"按当前未结单量定义，不考虑工单复杂度。
- 不覆盖人工在 Autotask 界面里手动分配的工单——本设计只管 agent 通过这个 MCP 服务做出的分配。
- 不保证这个服务进程有**多个副本**时也均衡——见技术设计「非功能」一节和下面的部署拓扑 Open question。

### 验收标准 AC1..ACn

- **AC1**：Given 一个队列有 2 名及以上在职的候选技术人员、且之前没有历史积压，When agent 在短时间窗口内（含并发）通过新流程分配 N 张工单，Then 各技术人员最终单量之差不超过 1（例如 10 张单分给 5 人 → 每人 2 张，而不是 10 张堆给一个人）。
- **AC2**：Given 一个队列只有 1 名在职候选技术人员，When 分配工单，Then 全部分给这个人，流程既不阻塞也不报错。
- **AC3**：Given 技术人员在新单到来前单量已经不均衡，When 分配这张新单，Then 它会分给该队列里当前未结单量最少的那个候选人（打平时按确定性规则判定）。
- **AC4**：Given 两次分配调用在几乎同一时刻发出（模拟 agent 同时处理多张单），When 两次调用都完成，Then 它们不能都基于同一份"谁单量最少"的快照行动——第二次调用的决定必须体现出第一次调用的结果，而不是一份过期的计数。
- **AC5**：Given 一个队列当前没有任何在职的候选技术人员，When agent 尝试往这个队列分配工单，Then 工具要报出一个明确、可处置的错误，而不是悄悄分给一个已离职/不在职的资源，也不是甩出一个不相关的 Autotask 报错。

### Open Questions

- [已假设] "均匀分布"按"该队列当前未结单量"理解，不按复杂度/时间加权负载，也不按技能匹配路由。如果业务实际想要的是按技能路由，AC1/AC3 和技术设计里的选人逻辑都要跟着变——留给 groom 确认。
- [已假设] "每个 level 的多个技术人员"按"服务同一个 Autotask 队列的多名在职技术人员"理解——队列是这个代码库里唯一现成能查到数据的分组维度（Autotask 的 `ResourceRoles` 按资源+角色+部门/队列记录，`autotask.service.ts:966-969`）。工单原文和 Jason Zhou 的评论都没有明确定义"level"；如果它实际指别的东西（角色层级、优先级层级），技术设计「改动清单」里的候选人查询需要相应调整。
- [不阻塞] 除了 Autotask 已有的 `isActive` 标志之外，请假/不在岗状态是否也应该把某个技术人员排除在"候选"之外——这个代码库目前接触到的数据里没有建模这个信息；在被告知之前默认只看 `isActive`。
- [不阻塞] 本仓库的 `docker-compose.yml` 显示的是单个服务、没有副本数配置，与"一个实例对应一个 Autotask 租户"的部署假设一致。如果运维以后对同一个 Autotask 租户跑多个该服务的副本，技术设计里的进程内锁就不够用了，需要换成共享锁（数据库行锁 / Redis）——这里只标记为风险，不在本单里解决，因为仅凭这个仓库看不出是否已经如此部署。

## 技术设计

### 结论

在本仓库新增一个 MCP 工具 `autotask_assign_least_loaded_resource`：它解析出该工单队列的候选技术人员集合，统计每个人在该队列当前的未结单量，把工单分给单量最少的那个人（打平按 `resourceID` 从小到大取），并把"读数-选人-写入"这整段流程放进一把以 `queueID` 为键的进程内异步锁里，让"同时"到达的调用改为串行执行，而不是在同一份过期计数上竞争。这直接照着 Jason Zhou 2026-10-20 的提案落地（一个原子工具，而不是靠 agent 侧的约定），并且复用本仓库已有的工单/资源查询基础设施——不引入新的外部依赖，也不改动现有工具的 schema。

### 现有实现定位

- 需要扩展的工单创建/更新入口：`tool.definitions.ts:553,664`、`tool.handler.ts:917-929`、`autotask.service.ts:579,592`。
- 可以原样复用的角色解析辅助函数：`tool.handler.ts:846`（`fillAssignedResourceRole`）+ `autotask.service.ts:1003`（`resolveRoleForResource`）——新工具选定资源后仍需要一个角色 ID，应该调用这个既有辅助函数，不要重复写一遍角色逻辑。
- 需要扩展的资源/角色查询：`autotask.service.ts:947`（`searchResourceRoles`）只能按资源查，目前没有反向的"按队列查"（需要新代码，见改动清单第 1 条）。
- 可以直接复用的工单计数能力：`autotask.service.ts:464`（`searchTickets`）已经接受任意的 `QueryFilter[]`（`tool.handler.ts:900-913` 用的就是同一套 `assignedResourceID` 等过滤器）；新工具可以复用它，加上 `queueID` 过滤 + `assignedResourceID in (...)` + 一个"未结"状态过滤——计数本身不需要新的查询原语。
- 本仓库里没有"先枚举候选、再行动"这种先例（在 `CHANGELOG.md` 与 `src/` 里搜 "least loaded" / "round robin" / "load balanc(e/ing)" 零命中)——下面的互斥锁写法对这个代码库是全新的，不是照抄哪个既有约定。

### 数据与接口契约

新工具：`autotask_assign_least_loaded_resource`

请求（`ticketID` / `createTicket` 必须恰好给一个）：

```json
{
  "queueID": 29682901,
  "ticketID": 123456,
  "createTicket": null,
  "roleName": "Help Desk"
}
```

或者一次调用完成"创建并分配"：

```json
{
  "queueID": 29682901,
  "ticketID": null,
  "createTicket": { "companyID": 29683561, "title": "..." },
  "roleName": null
}
```

（`createTicket` 的形状和 `autotask_create_ticket` 现有的一样，只是去掉 `assignedResourceID`——这个字段是计算出来的，不是调用方传入的。）

响应：

```json
{
  "result": {
    "ticketID": 123456,
    "assignedResourceID": 207,
    "assignedResourceRoleID": 44,
    "consideredResources": [
      { "resourceID": 207, "openTicketCount": 3 },
      { "resourceID": 311, "openTicketCount": 3 },
      { "resourceID": 455, "openTicketCount": 7 }
    ]
  },
  "message": "Assigned ticket 123456 to resource 207 (3 open tickets in queue 29682901, lowest among 3 eligible)"
}
```

错误：`queueID` 下零个在职候选资源时，抛出一个明确指名该队列的 `NoEligibleResourceError`——不是一个泛泛的 Autotask 错误（对应 AC5）。

向后兼容：纯增量改动。`autotask_create_ticket`（`:553`）/ `autotask_update_ticket`（`:664`）不变——想明确指定某个技术人员的 agent 仍然可以照旧调用；这是它们之外一个新的可选工具，不是替代品。

### 关键流程时序

```
Agent -> autotask_assign_least_loaded_resource(queueID, ticketID | createTicket)
  tool.handler.ts: queueLock.run(queueID, async () => {
    1. resources = autotaskService.getEligibleResourcesForQueue(queueID)
       -> 若 resources.length === 0：抛出 NoEligibleResourceError(queueID)
    2. counts = autotaskService.countOpenTicketsByQueueAndResource(queueID, resources.map(r => r.resourceID))
    3. chosen = 单量最少的资源（打平按 resourceID 从小到大取）
    4. fillAssignedResourceRole(payload, roleName)   // 既有辅助函数，tool.handler.ts:846
    5. 若有 ticketID：autotaskService.updateTicket(ticketID, { assignedResourceID: chosen, ... })
       否则：        autotaskService.createTicket({ ...createTicket, assignedResourceID: chosen, ... })
  })
  <- 返回结果里带选中的 resourceID 和参考过的各家计数，便于事后核对
```

因为第 1-5 步都包在同一个 `queueLock.run(queueID, ...)` 里，同一个 `queueID` 的第二次调用如果在第一次还处于第 1-5 步之间就到达，会一直等到第一次结束，再重新读计数——这时它会看到第一张单已经被算进去了。这就是满足 AC4 的机制。

### 非功能

- **幂等与并发**：以队列为键的进程内异步锁（`queue-lock.ts`）把同一队列内的重叠调用串行化——这是本改动能堵住的唯一失效模式。不同队列之间并行执行，不会被不必要地串行化。
- **性能**：计数只是一次 `searchTickets` 查询，规模受候选资源数量限制（通常一个队列也就几名技术人员）。不加缓存；按常见 MSP 工单量，预计不会成为新的热点路径。工单本身没有提出数字化的性能指标，这里不替它编一个——如果有，应该在 groom 里补充。
- **安全**：不引入新的鉴权面。这个工具和服务里其它工具用的是同一套 Autotask 凭据（`AUTOTASK_USERNAME`/`AUTOTASK_SECRET`，`docker-compose.yml`）——没有新密钥、没有新权限范围。
- **多租户隔离**：这个 MCP 服务本来就是"一个部署实例对应一个 Autotask 租户"（`.env`/`docker-compose.yml` 里一套凭据）。本改动不引入任何跨租户的接触面，这条既有的隔离边界不受影响。这个代码库内部也没有再进一步的"租户"维度需要隔离——下面「测试用例」一节专门说明了为什么常规的多租户用例条目在这里换了一种落法。
- **可观测性**：通过既有的 `this.logger`（和 `createTicket` 里 `:584` 的 `this.logger.info` 用法一致）在 `info` 级别记下完整决策（queueID、每个候选人的计数、最终选中的 resourceID），这样事后可以核对一次可疑的分配结果，而不是面对一个没人能解释的数字。

### 上线与回滚

纯增量改动——新增一个工具名，不改任何现有工具的行为或 schema。走本仓库常规发布流程（历史上有可比的增量改动，例如 `ab1aaf6 feat(billing-codes): add autotask_search_billing_codes`)。回滚即还原这次提交；不涉及数据迁移，也不需要开关，因为没有任何现有调用方依赖这个新工具存在。

### 测试策略

- **风险**："均匀"被假设为"未结单量相等"（见上面 Open question）；如果产品实际想要别的定义，改动清单第 1-2 条的查询形状要跟着调整，但锁与选人架构（第 3、5 条）不受影响。
- **依赖**：部署拓扑（单实例还是多副本）单凭这个仓库看不出来（`docker-compose.yml` 只有一个 service、没有副本数配置）——如果运维对同一个 Autotask 租户跑了不止一个实例，进程内锁就不够用了，需要换成共享锁（数据库行锁 / Redis），这超出本单范围，除非被确认确实需要。
- **依赖**：未发现依赖本队列中其它在途工单——`CHANGELOG.md` 里没有其它 PRD 引用这个仓库的工单分配路径。

## 测试用例

（判定句写在这里；完整步骤在同目录的 `PRD-20620.ac.json` 里）

- **TC1**（AC1，自动）：Given 一个队列有 5 名在职候选技术人员且各自从 0 张未结单开始，When 通过 `autotask_assign_least_loaded_resource` 并发分配 10 张工单，Then 每个人最终恰好拿到 2 张（最大-最小之差 ≤ 1）。
- **TC2**（AC2，自动）：Given 一个队列只有 1 名在职候选技术人员，When 分配 5 张工单，Then 全部 5 张都分给这个人，且没有任何调用报错。
- **TC3**（AC3，自动）：Given 3 名候选技术人员现有未结单量分别是 5、0、3，When 分配 1 张新单，Then 它分给单量为 0 的那个人。
- **TC4**（AC4，自动）：Given 同一队列的两次分配调用被安排成——如果不串行化，它们内部的计数步骤会重叠，When 两次调用都完成，Then 第二次调用的结果要体现第一次调用的结果——两次调用不会都基于同一份过期计数选中同一个人。
- **TC5**（AC5，自动）：Given 一个队列零个在职候选技术人员，When 分配一张工单，Then 工具抛出一个明确的 `NoEligibleResourceError`，且 `createTicket`/`updateTicket` 都不会被调用。
- **TC6**（AC1，手工——本地盲区，未执行）：Given 一个真实 Autotask 沙箱/INT 环境里某队列有 3 名及以上在职技术人员，When 通过新工具创建 5 张带测试前缀的工单，Then Autotask 界面显示的受理人按"未结单量最少"规则分散开，且每张单的 `assignedResourceID` 都和工具返回的一致。本沙箱无法执行（没有 Autotask 凭据）；需要实现完成后由 dev/QA 在有真实访问权限的环境里补做。

**权限/多租户测试说明**：这个代码库没有可测的跨租户边界——一个部署实例对应一个 Autotask 租户的一套凭据（见技术设计「非功能」一节）。这里能找到的最接近的类比是"按队列隔离"，已经被 TC1/TC3（计数和选人从不跨队列）和 TC5（候选人为空是按队列判定的，不是全局的）覆盖到。如实记录为什么常规的多租户用例条目在这里不适用，而不是悄悄省略它。

## 需求理解

一句话：把 `autotask_assign_least_loaded_resource` 工具改成由调用方直接传入一份候选技术人员清单（每项带 `resourceID` 与 `roleID`）、一个工单状态、以及一个可选的队列 ID 列表，而不是传一个 `queueID` 让工具自己去 Autotask 查谁符合条件；工具应该只按给定的 status/queue 过滤条件统计清单里每个人的现有单量，分给单量最少的人（保留现有的串行+锁机制），并返回更结构化的结果。

Lucas Chen 的评论（2026-10-21，完整引用见下方"工单往来"）给出了一个示例：

```json
{
  "ticketID": 12345,
  "status": 8,
  "queueIDs": [29682833],
  "technicians": [
    {"resourceID": 29684013, "roleID": 29683462},
    {"resourceID": 29684035, "roleID": 29682834}
  ]
}
```

这是对 Carl Zhang 原始反馈（2026-10-15：并发分配工单会全部落到同一个人身上而不是均匀分散）的一次细化——"均匀分配"这个大目标没变；变的是由谁来判定"符合条件"（现在是调用方，不再是本工具查 Autotask）、以及"单量"的统计口径（现在是明确的 status + 可选 queue 过滤，不再是写死的"未完成"假设）。

## 产品设计

### 目标 / 非目标

目标（沿用第一轮，实质不变）：
- 当多次工单分配在短时间内发生（包括并发发生）时，被考虑范围内的技术人员负载应大致均衡——不应聚集在最先被点名的那个人身上。
- 修复必须在真正并发的情况下成立，不能只在严格串行处理时才成立。

目标（本轮新增）：
- 由调用方（而不是本工具）决定谁符合条件——工具必须接受明确的 `technicians` 清单，不得自己去查 Autotask 的队列归属。
- "负载"必须能按调用方指定的工单 `status` 计数，并可选按调用方指定的队列集合（`queueIDs`）收窄范围，而不是本工具内部写死的"未完成"假设。
- 返回结果必须结构化：调用方需要的每一项事实（选中了谁、他的角色、统计了什么、在什么过滤条件下）都必须是 `result` 里的具名字段，不能要求调用方去解析 `message` 字符串。

非目标（沿用第一轮）：
- 不重新设计 Autotask 的队列/角色模型。
- 不做按技能或优先级加权的路由——"均衡"仍然是当前匹配单量，不是复杂度。
- 不覆盖人工在 Autotask 界面里手动分配的工单。
- 不保证本服务进程多个**副本**之间的均衡分配（和第一轮同样的保留意见——锁是进程内的）。

非目标（本轮新增，是契约改动的直接后果）：
- 本工具不再负责判定"谁符合某个队列的资格"——这个职责整体移交给调用方。第一轮的 `getEligibleResourcesForQueue` / Autotask `ResourceRoles` 查询对本工具而言成为死代码（见技术设计"改动清单"）。
- 不校验调用方给的 `technicians` 清单本身是否正确（比如每个 `resourceID` 是否真的在职、是否真的服务于某个队列）——工具信任调用方给的清单，就像第一轮之前 `autotask_create_ticket`/`autotask_update_ticket` 一直信任调用方给的 `assignedResourceID` 一样。

### 验收标准 AC1..AC8

- **AC1**（原 AC1，改写）：给定 `technicians` 数组有 2 个或以上条目、且按给定 `status`/`queueIDs` 过滤条件当前都没有匹配单，当 agent 在短时间窗口内（包括并发）通过本工具分配 N 张单时，则每个清单内技术人员最终的匹配单量之差不超过 1。
- **AC2**（原 AC2，不变）：给定 `technicians` 恰好有 1 个条目，当分配若干张单时，则全部分给这一个人，且流程不阻塞、不报错。
- **AC3**（原 AC3，改写）：给定清单内技术人员分配前已有不均衡的匹配单量，当一张新单被分配时，则分给清单内当前匹配单量最少的那个人（打平时按最小 `resourceID` 确定性决胜）。
- **AC4**（原 AC4，改写）：给定两次分配调用针对相同或重叠的 `technicians`/`status`/`queueIDs` 组合、且几乎同一时刻发出，当两次调用都完成后，则第二次调用的判断必须反映第一次调用写入后的结果，不能停留在过期的匹配单量快照上。
- **AC5**（原 AC5，改写）：给定 `technicians` 缺失或为空数组，当 agent 尝试分配工单时，则工具必须报出一个明确、可据此行动的错误，而不是悄悄失败或瞎猜一个资源。
- **AC6**（新增）：给定 `status` 和/或 `queueIDs` 过滤条件，当统计清单内每个技术人员的当前负载时，则只有匹配该 status（若给了 `queueIDs`，还要匹配其中某个队列）的工单才计入该技术人员的负载——过滤条件之外的其它工单不得影响其计数。
- **AC7**（新增）：给定一次成功的分配，当工具返回结果时，则 `result` 必须包含明确的具名字段：被分配的 `ticketID`、选中的 `assignedResourceID` 与 `assignedResourceRoleID`、实际生效的过滤条件（`status`、`queueIDs`）、以及每个被考虑的技术人员的匹配单量——调用方必须能不解析 `message` 自由文本就拿到以上每一项事实。
- **AC8**（新增）：给定使用 `createTicket`（没有现成的 `ticketID`）且 `queueIDs` 为空数组或包含 2 个及以上条目，当调用本工具时，则必须报出一个明确的校验错误，要求恰好提供一个队列 ID 用于新建工单——新建的单需要恰好一个归属队列，而 `queueIDs` 作为"计数用的过滤条件"（不是"这张单该进哪个队列"字段）会在这种情况下产生歧义。

### Open Questions

- [已假设 / assumed，不阻塞] `queueIDs` 按数组解读，依据是 Lucas Chen 的 JSON 示例（`"queueIDs": [29682833]`），尽管原文说的是单数"queueid(可选)"——以示例为准，而不是以口语化的原文表述为准。如果原意确实是单个标量，受影响的只是数据接口的形状，AC 本身不受影响。
- [已假设 / assumed，不阻塞] `queueIDs` 是可选的（按原文"可选"二字）；省略时按 `status` 在全部队列范围内统计。`status` 本身视为必填（原文列出它时没有标"可选"，这点和 `queueIDs` 不同）。
- [已假设 / assumed，不阻塞] 保留 `createTicket` 选项（与 `ticketID` 二选一，和第一轮一致），尽管 Lucas Chen 的示例只展示了 `ticketID`——需求里没有任何一句话要求去掉创建并分配的路径，在没人要求的情况下砍掉一个刚上线的能力，是另一个方向上的范围蔓延。AC8 是因此唯一需要补的新规则。

## 技术设计

### 结论

就地修改 `autotask_assign_least_loaded_resource`（不新增第二个工具）：用调用方提供的 `technicians` 数组取代 `queueID` 自动发现，用调用方提供的 `status`（+ 可选 `queueIDs`）过滤条件取代写死的"未完成"假设，去掉 Autotask 角色解析步骤、改为直接使用调用方按人提供的角色，并返回完全结构化的结果。这直接落实 Lucas Chen 2026-10-21 的评论；作为副作用，它还顺带去掉了第一轮最大的风险项（未经确认的 Autotask"队列 → 符合条件的资源"查询形状），因为这次查询已经不再需要。

### 现有实现定位

精确的 `path:line` 引用见上面"现状"一节：`tool.definitions.ts:730-793`（schema）、`tool.handler.ts:944-999`（分发）、`autotask.service.ts:1043-1096`（`getEligibleResourcesForQueue` + `countOpenTicketsByQueueAndResource`）、`queue-lock.ts`（仅锁 key 需要改）。

### 数据与接口契约

请求（`ticketID`/`createTicket` 二选一，与第一轮一致）：

```json
{
  "ticketID": 12345,
  "status": 8,
  "queueIDs": [29682833],
  "technicians": [
    {"resourceID": 29684013, "roleID": 29683462},
    {"resourceID": 29684035, "roleID": 29682834}
  ]
}
```

`queueIDs` 可省略（省略时按给定 `status` 在全部队列范围内统计）。使用 `createTicket` 而不是 `ticketID` 时，`queueIDs` 必须恰好包含 1 个条目（AC8）——这个条目就是新单的 `queueID`，和第一轮在创建路径上设置 `payload.queueID = queueID` 的做法一致。

响应（按 AC7 结构化——调用方需要的每一项都是具名字段，`message` 只是便于阅读的摘要）：

```json
{
  "result": {
    "ticketID": 12345,
    "assignedResourceID": 29684035,
    "assignedResourceRoleID": 29682834,
    "appliedFilter": { "status": 8, "queueIDs": [29682833] },
    "consideredTechnicians": [
      { "resourceID": 29684013, "roleID": 29683462, "matchingTicketCount": 3 },
      { "resourceID": 29684035, "roleID": 29682834, "matchingTicketCount": 1 }
    ]
  },
  "message": "Assigned ticket 12345 to resource 29684035 (1 matching ticket, lowest among 2 listed technicians)"
}
```

错误：
- `technicians` 缺失或为空 → 明确报错（例如 `NoCandidateTechniciansError`），`createTicket`/`updateTicket` 都不会被调用（AC5）。
- 用 `createTicket` 且 `queueIDs` 长度为 0 或 ≥2 → 明确的校验错误，说明"创建工单时必须恰好提供一个 queueIDs 条目"（AC8）。

向后兼容性：**这是一次破坏性变更**，对象是第一轮刚上线并发布的契约（见"现状"一节——下方"风险与依赖"说明为什么仍然接受这个代价）。

### 关键流程时序

```
Agent -> autotask_assign_least_loaded_resource(ticketID | createTicket, status, queueIDs?, technicians)
  tool.handler.ts:
    1. 校验 technicians 非空（否则 NoCandidateTechniciansError）
    2. 校验 ticketID/createTicket 恰好给一个（与第一轮一致，TC-DEV1）
    3. 若是 createTicket：校验 queueIDs.length === 1（否则校验错误，AC8）
    4. lockKey = `${status}|${排序后的(queueIDs ?? [])}|${排序后的 technicians.map(t => t.resourceID)}`
    5. assignmentLock.run(lockKey, async () => {
         a. counts = autotaskService.countMatchingTicketsByResource(status, queueIDs, technicians.map(t => t.resourceID))
         b. chosen = 计数最小的技术人员，打平按最小 resourceID 决胜
         c. payload.assignedResourceID = chosen.resourceID
            payload.assignedResourceRoleID = chosen.roleID   // 不再需要查 Autotask 角色
            若是 createTicket: payload.queueID = queueIDs[0]
         d. ticketID != null ? updateTicket(ticketID, payload) : createTicket(payload)
       })
  <- 结构化结果（AC7）：ticketID、assignedResourceID、assignedResourceRoleID、appliedFilter、consideredTechnicians
```

因为步骤 5 整体跑在一个 `assignmentLock.run(lockKey, ...)` 里，第二个 `lockKey` 重叠的调用（相同的 status/queueIDs/technicians）在第一个调用还处于 (a) 到 (d) 之间时会等待，等第一个调用完成后再重新读取、读到的计数已经包含第一个调用的写入——和第一轮同样的机制、同样的 AC4 保证，只是换了 key 的范围。

### 非功能

- **幂等与并发**：同一个 `KeyedAsyncLock`，key 换了（见上）。`technicians`/`status`/`queueIDs` 组合完全不重叠的两次调用之间不再互相等待——比第一轮只按队列加锁的粒度更并行一些，因为不共享统计数据的调用不再被无谓地串行化。
- **性能**：每次调用一次 `Tickets` 查询，开销随 `technicians` 清单长度线性增长（形状与第一轮一致，只是过滤条件变了）。
- **安全**：不变——同一套 Autotask 凭据，没有新的密钥或权限范围。
- **多租户隔离**：和第一轮一致——每个部署实例对应一个 Autotask 租户，本次改动不引入跨租户面。
- **可观测性**：在 `info` 级别记录完整决策过程（锁 key、每个候选人的匹配单量、最终选中的资源），延续第一轮在这个调用点已有的日志惯例。

### 上线与回滚

和第一轮纯增量式不同，这**确实**是对一个发布才几个小时的工具的破坏性变更。上线：按普通提交走这个仓库的常规发布流程，直接改同一个工具名——需求本身没有要求灰度或双契约过渡期，这里也不替它发明一个。回滚：回退这个提交即可恢复第一轮的 `queueID` 契约；由于生产环境进入第一轮契约才几个小时，往哪个方向回退，"中途切过去的调用方"这个爆炸半径是对称的。这一点在下方"风险与依赖"标出，不在此处解决，因为本沙盒看不到网关调用日志，无法确认是否已经有调用方接上了第一轮的形状。

### 测试策略

仅单元测试，和第一轮同样的限制（本沙盒没有真实 Autotask 凭据——见测试用例 TC9，沿用第一轮未变的本地盲区）。改写 `tests/assign-least-loaded.test.ts` 以适配新参数形状；mock 方式（`AutotaskService` mock、并发用例的路由式 fetch mock）照搬第一轮不变。

### 风险与依赖

- **风险**：对几小时前刚发布的契约做破坏性变更——如果除了本功能自己的 agent 编排层之外，已经有别的调用方接上了 `queueID` 契约，这次改动会让它们失败。本沙盒看不到网关调用日志，无法两边都确认；标出来提醒合并这次改动的人先跟团队确认一下（不阻塞设计本身，因为 Lucas Chen 的要求对新形状说得很明确）。

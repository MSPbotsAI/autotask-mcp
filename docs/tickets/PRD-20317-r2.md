## Rework judgement

**Type: Dev error (implementation defect + test gap), not a requirement change.**

**Basis**: QA `[TEST · PRD-20317]` comment `90170265051691` (Minnie Zhou, 2026-10-21), tested against INT `autotask-mcp main@29d71f7` (contains `83091b7`, the r1 commit). Conclusion: FAIL — with `includeUserDefinedFields: true` the call errors on the real Autotask API and returns no contacts, so the feature is not usable; default behavior (flag omitted or `false`) is unchanged and passes.

**What was wrong (r1)**: `tool.handler.ts`'s `autotask_search_contacts` branch set `includeFields: [...SUMMARY_FIELDS.contacts, 'userDefinedFields']` whenever the flag was on, and `AutotaskService.searchContacts()` forwarded that straight into the Autotask query's `IncludeFields`. Autotask rejects `userDefinedFields` as a value inside `IncludeFields` and returns HTTP 500 `Unable to find userDefinedFields in the Contact Entity`. This was exactly the risk the r1 tech design flagged under Open Questions / Non-functional / Risks (whether Autotask's `IncludeFields` is additive or restrictive was unconfirmed, and live verification could not be performed in that sandbox either — see r1's "Known local gap") — but the mitigation chosen (always send an explicit superset) turned out to still be wrong, for a different reason than the one anticipated: the field name itself isn't a valid `IncludeFields` entry at all, independent of additive/restrictive semantics.

**What changed this round**: the chosen wiring for the opt-in flag's query construction, not the product requirement. AC1–AC6 and the product design's Goals/Non-goals in `docs/tickets/PRD-20317.md` are unchanged and still govern this round — see that document for the full product design and original tech design narrative. Only the specific mechanism by which `searchContacts()` is called changes (dev's own authority under `legs/dev.md` S1/`references/docs-tree.md` §57 note 2: tech design is dev's to change as long as user-visible behavior doesn't move).

**Live verification**: still not performed by this leg — this sandbox has no network path to Autotask and no Autotask credentials configured (confirmed: no `AUTOTASK_*` keys in either `.env` location). Recorded here per instruction rather than claimed; see Self-test "Known local gap" below. QA's own live test against INT (comment `90170265051691`) is the only live confirmation of the root cause so far, and this round's mock was rewritten specifically to match what that live test observed.

### Tech design update (r2)

Supersedes r1's "Where the current implementation lives" / "Change list" entries for `tool.handler.ts`'s `autotask_search_contacts` handler and (by removal) `src/services/autotask.service.ts`'s `includeFields` forwarding path for this call site only:

- `src/handlers/tool.handler.ts` (`autotask_search_contacts` branch, was line ~904-914, see r1 "Where the current implementation lives"): no longer builds an `includeFields` superset. It still strips `includeUserDefinedFields` from the args before calling the service, but always calls `s.searchContacts(rest)` with no `includeFields` key at all, regardless of the flag's value.
- `src/services/autotask.service.ts`'s `searchContacts()` (line ~328-362): **unchanged**. Its `options.includeFields?.length` gate is now dead for this call site (no caller passes it), but the gate itself is generic, harmless, and documented — removing it is out of scope for a targeted bug fix and would widen the diff without benefit. No other call site in the repo sets `AutotaskQueryOptions.includeFields` (confirmed via `grep -rn includeFields src/`).
- `src/utils/response.formatter.ts` (`pickSummaryFields`/`formatCompactResponse`/`extraFields`): **unchanged, and this is the point** — it was already correct. It reads `userDefinedFields` off the *raw* item returned by Autotask (which, per real-API behavior observed by QA, includes every field by default whenever no `IncludeFields` is sent) and only copies it into the compact response when the caller's `extraFields` includes it (gated on `args.includeUserDefinedFields`, untouched in `tool.handler.ts`'s shared compact-response call site). The opt-in gating the ticket asked for was always happening at the formatter layer, not at the Autotask query layer — r1's mistake was adding an unnecessary and incorrect second gate at the query layer.
- `src/handlers/tool.handler.ts`'s import line (line 9): `SUMMARY_FIELDS` import removed — it has no remaining use in this file after the above change, and this repo's `tsconfig.json` has `noUnusedLocals: true` (would fail `tsc --noEmit` otherwise). `SUMMARY_FIELDS` itself remains exported from `response.formatter.ts` for its other consumer (the formatter itself).

Net effect: fewer moving parts than r1, same user-visible contract (AC1-AC6 unchanged), and the one Autotask-rejected request shape is now structurally impossible to send from this call site.

### Open question for the reporter (unchanged from QA, not resolved by dev)

QA's low-priority item, carried forward verbatim because it requires a product decision, not an implementation choice:

> TC3 expects no `userDefinedFields` key when a contact has no custom fields set, but Autotask usually returns every UDF with value `null`. Please confirm the expected behavior with the reporter: keep the null entries, or filter them out in the formatter, and align TC3 with the real response.

**Not changed in this round.** TC3's text and the implementation's behavior (pass through whatever Autotask returns; the formatter copies `userDefinedFields` from the raw item unmodified, filtering nothing) are left exactly as r1 defined them. This is a potential test-fixture/AC mismatch with real-world Autotask data (our fixture models a contact with `userDefinedFields: []`; if real Autotask instead returns an array of every UDF with `value: null`, TC3 still passes under our fixture but the fixture itself may not represent reality) — flagged for the reporter to confirm, not resolved by assumption here, per the instruction not to change TC3 or the behavior to appease it. See Self-test "Test case matrix" below for how TC3 was actually re-run this round.

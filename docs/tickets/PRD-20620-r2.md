## Requirement understanding

One line: Change the `autotask_assign_least_loaded_resource` tool so the caller passes an explicit list of candidate technicians (each with `resourceID` and `roleID`), a ticket status, and an optional list of queue IDs, instead of a single `queueID` that the tool uses to look up eligible technicians from Autotask itself; the tool should count only the tickets matching that status/queue filter for each listed technician, assign to whichever has the fewest (keeping the existing serial+lock behavior), and return a more structured result.

Lucas Chen's comment (2026-10-21, quoted in full under "Ticket thread" below) gives a worked example:

```json
{
  "ticketID": 12345,
  "status": 8,
  "queueIDs": [29682833],
  "technicians": [
    {"resourceID": 29684013, "roleID": 29683462},
    {"resourceID": 29684035, "roleID": 29682834}
  ]
}
```

This is a refinement of the same underlying complaint Carl Zhang filed (2026-10-15: concurrent ticket assignment collapses onto one technician instead of spreading evenly) — the even-distribution goal is unchanged; what changed is who determines "eligible" (now the caller, not this tool via an Autotask query) and how "load" is scoped (now an explicit status + optional queue filter, not a fixed "not complete" assumption).

## Product design

### Goals / Non-goals

Goals (carried over from round 1, unchanged in substance):
- When several ticket assignments happen close together (including concurrently), load should end up roughly even across the technicians under consideration — not clustered on whichever technician is named first.
- The fix must hold under true concurrency, not only strict sequential processing.

Goals (new this round):
- The caller (not this tool) determines who is eligible — the tool must accept an explicit `technicians` list and must not query Autotask for queue membership on its own.
- "Load" must be countable against a caller-specified ticket `status`, optionally narrowed to a caller-specified set of queues (`queueIDs`), instead of a fixed "not complete" assumption baked into this tool.
- The result must be structured: every fact a caller needs (who was chosen, their role, what was counted, under what filter) must be a typed field in `result`, not something the caller has to parse out of the `message` string.

Non-goals (carried over from round 1):
- Not redesigning Autotask's queue/role model.
- Not implementing skill-based or priority-weighted routing — "even" is still current matching-ticket count, not complexity.
- Not covering tickets a human assigns manually in the Autotask UI.
- Not guaranteeing even distribution across multiple *replicas* of this server process (same caveat as round 1 — the lock is in-process).

Non-goals (new this round, as a direct consequence of the contract change):
- This tool no longer determines *who is eligible* for a queue — that responsibility moves entirely to the caller. Round 1's `getEligibleResourcesForQueue` / Autotask `ResourceRoles` query becomes dead code for this tool's purposes (see Tech design "Change list").
- Not validating that the caller's `technicians` list is actually correct (e.g., that each `resourceID` really is active, or really does serve the stated queue) — the tool trusts the caller-supplied list, same way it already trusted a caller-supplied `assignedResourceID` on `autotask_create_ticket`/`autotask_update_ticket` before round 1 existed.

### Acceptance criteria AC1..AC8

- **AC1** (was AC1, reworded): Given a `technicians` array of 2 or more entries where none currently has a matching ticket (per the given `status`/`queueIDs` filter), when the agent assigns N tickets through the tool within a short window (including concurrently), then the resulting matching-ticket counts per listed technician differ by at most 1.
- **AC2** (was AC2, unchanged): Given `technicians` has exactly 1 entry, when tickets are assigned, then they all go to that technician and the flow neither blocks nor errors.
- **AC3** (was AC3, reworded): Given the listed technicians already have uneven matching-ticket counts before a new ticket arrives, when that ticket is assigned, then it goes to whichever listed technician currently has the fewest matching tickets (ties broken deterministically by lowest `resourceID`).
- **AC4** (was AC4, reworded): Given two assignment calls are issued for an overlapping or identical `technicians`/`status`/`queueIDs` combination at effectively the same instant, when both complete, then the second call's decision must reflect the first call's result, not a stale snapshot of matching-ticket counts.
- **AC5** (was AC5, reworded): Given `technicians` is missing or an empty array, when the agent tries to assign a ticket, then the tool reports this as a distinct, actionable error rather than silently failing or guessing a resource.
- **AC6** (new): Given a `status` and/or `queueIDs` filter, when counting each listed technician's current load, then only tickets matching that status (and, if `queueIDs` is given, also in one of those queues) count toward that technician's load — a technician's other tickets outside the filter must not inflate or deflate their count.
- **AC7** (new): Given a successful assignment, when the tool returns its result, then `result` contains explicit, typed fields for the assigned `ticketID`, the chosen `assignedResourceID` and `assignedResourceRoleID`, the filter that was applied (`status`, `queueIDs`), and each considered technician's matching-ticket count — a caller must be able to get every one of these facts without parsing the free-text `message`.
- **AC8** (new): Given `createTicket` is used (no pre-existing `ticketID`) and `queueIDs` contains zero or more than one entry, when the tool is invoked, then it reports a distinct validation error requiring exactly one queue ID to create a new ticket into — a brand-new ticket needs exactly one destination queue, and `queueIDs` being a filter-for-counting (not a "the ticket's queue" field) makes this ambiguous otherwise.

## Tech design

### Conclusion

Modify `autotask_assign_least_loaded_resource` in place (do not add a second tool) to replace `queueID`-based auto-discovery with a caller-supplied `technicians` array, replace the fixed "not complete" status assumption with a caller-supplied `status` (+ optional `queueIDs`) filter, drop the Autotask role-resolution step in favor of the role the caller already supplies per technician, and return a fully structured result. This directly implements Lucas Chen's 2026-10-21 comment and, as a side effect, removes round 1's single biggest Risk (the unconfirmed Autotask "queue → eligible resources" query shape) since that query is no longer needed.

### Data & API contract

Request (exactly one of `ticketID` / `createTicket`, same as round 1):

```json
{
  "ticketID": 12345,
  "status": 8,
  "queueIDs": [29682833],
  "technicians": [
    {"resourceID": 29684013, "roleID": 29683462},
    {"resourceID": 29684035, "roleID": 29682834}
  ]
}
```

`queueIDs` may be omitted (counts across all queues for the given `status`). When `createTicket` is used instead of `ticketID`, `queueIDs` must contain exactly 1 entry (AC8) — that entry becomes the new ticket's `queueID`, the same way round 1 set `payload.queueID = queueID` on the create path.

Response (structured per AC7 — every field a caller needs is typed, `message` is a convenience summary only):

```json
{
  "result": {
    "ticketID": 12345,
    "assignedResourceID": 29684035,
    "assignedResourceRoleID": 29682834,
    "appliedFilter": { "status": 8, "queueIDs": [29682833] },
    "consideredTechnicians": [
      { "resourceID": 29684013, "roleID": 29683462, "matchingTicketCount": 3 },
      { "resourceID": 29684035, "roleID": 29682834, "matchingTicketCount": 1 }
    ]
  },
  "message": "Assigned ticket 12345 to resource 29684035 (1 matching ticket, lowest among 2 listed technicians)"
}
```

Errors:
- `technicians` missing or empty → distinct error naming the problem (e.g. `NoCandidateTechniciansError`), neither `createTicket` nor `updateTicket` is invoked (AC5).
- `createTicket` given with `queueIDs` of length 0 or 2+ → distinct validation error naming the requirement ("exactly one queueIDs entry required when creating a ticket") (AC8).

Backward compatibility: **this is a breaking change** to the contract round 1 shipped and released (see "Current state" — the Risks section below covers why this is accepted anyway).

### Key flow / sequence

```
Agent -> autotask_assign_least_loaded_resource(ticketID | createTicket, status, queueIDs?, technicians)
  tool.handler.ts:
    1. validate technicians non-empty (else NoCandidateTechniciansError)
    2. validate exactly one of ticketID/createTicket (unchanged from round 1, TC-DEV1)
    3. if createTicket: validate queueIDs.length === 1 (else validation error, AC8)
    4. lockKey = `${status}|${sorted(queueIDs ?? [])}|${sorted(technicians.map(t => t.resourceID))}`
    5. assignmentLock.run(lockKey, async () => {
         a. counts = autotaskService.countMatchingTicketsByResource(status, queueIDs, technicians.map(t => t.resourceID))
         b. chosen = technician with min(counts), tie-break by lowest resourceID
         c. payload.assignedResourceID = chosen.resourceID
            payload.assignedResourceRoleID = chosen.roleID   // no Autotask role lookup needed any more
            if createTicket: payload.queueID = queueIDs[0]
         d. ticketID != null ? updateTicket(ticketID, payload) : createTicket(payload)
       })
  <- structured result (AC7): ticketID, assignedResourceID, assignedResourceRoleID, appliedFilter, consideredTechnicians
```

Because step 5 runs inside one `assignmentLock.run(lockKey, ...)`, a second call with an overlapping `lockKey` (same status/queueIDs/technicians) arriving while the first is between (a) and (d) waits until the first finishes, then re-reads counts that include the first call's write — same mechanism round 1 used, same AC4 guarantee, scoped to the new key.

### Non-functional

- **Idempotency & concurrency**: same `KeyedAsyncLock`, new key (see above). Two calls with disjoint `technicians`/`status`/`queueIDs` combinations never wait on each other — slightly more parallelism than round 1's per-queue-only key, since calls that don't actually share counted ticket data no longer serialize unnecessarily.
- **Performance**: one `Tickets` query per call, bounded by the `technicians` list length (same shape as round 1, filter changed).
- **Security**: unchanged — same Autotask credentials, no new secret or scope.
- **Multi-tenant isolation**: unchanged from round 1 — one Autotask tenant per deployed instance, no cross-tenant surface introduced.
- **Observability**: log the full decision (lock key, each candidate's matching count, the chosen resource) at `info`, same as round 1's logging convention at this call site.

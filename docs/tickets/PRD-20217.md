# PRD-20217 · autotask_create_contact: default isActive to 1 when omitted

Status: frozen @ 5c34372 (code commit; this doc is committed separately afterwards)
Ticket: https://app.clickup.com/t/86e3nb1bv
Repo: https://github.com/MSPbotsAI/autotask-mcp · base `main` @ `9700dde` · work branch `dev01.mbagent/PRD-20217`

## Background

The original issue (`POST /Contacts` returning an IIS 404) was fixed by Leo Yang in `8661536` and released to PRD with `9700dde` on 2026-10-12.
QA (Pantene Hui) reported a follow-up on 2026-10-15: calls now reach Autotask but often fail on the first attempt:

> Autotask POST /Companies/29683561/Contacts failed: HTTP 500: Missing Required Field: isActive.

Evidence (sopId 974, prod, 2026-10-14): T20261014.0023 / .0027 / .0029 failed first and succeeded on retry; T20261014.0033 failed with no retry, so no contact was created.
The skill already tells the agent to pass `isActive=1`; the model still omits it most of the time, so a prompt-level fix is not reliable.

## Source of requirements

This ticket has **no design-leg product design, tech design or test cases**. Acceptance criteria come straight from QA's 2026-10-15 comment; **the test cases were written by dev and have not been through groom** — reviewers please take an extra look.

QA acceptance criteria:

1. Calling `autotask_create_contact(companyID, firstName, lastName)` without `isActive` creates an active contact with no HTTP 500.
2. Re-run one onboarding ticket and confirm `Created Autotask contact <name>` on the first attempt. (Needs PRD — see "not executed".)

## Root cause (code evidence, base 9700dde)

- `src/handlers/tool.definitions.ts:345`: the `autotask_create_contact` `inputSchema` lists companyID / firstName / lastName / emailAddress / phone / title only — **no `isActive`**, so the model never sees it.
- `src/handlers/tool.handler.ts:892` passes the args object straight to `createContact`.
- `src/services/autotask.service.ts:366`: `createContact` forwards it unchanged to `POST /Contacts` and to the 404 fallback `POST /Companies/{id}/Contacts`, **with no defaults**.
- The Autotask Contacts entity requires `isActive` (`src/types/autotask.ts:31`: numeric, not boolean).

## Change

| File | Change |
| `src/services/autotask.service.ts` | `createContact` builds the body once, before both routes: `isActive: input.isActive ?? 1`. An explicit 0 is kept; the caller's object is not mutated |
| `src/handlers/tool.definitions.ts` | `autotask_create_contact` input gains `isActive` (number, `default: 1`, described as "defaults to 1 when omitted"). Not added to `required`, since the server fills it in |
| `tests/contact-create-isactive.test.ts` | 6 new cases asserting on the request body actually sent |

Rationale: the default lives in the service layer (the single request exit), not the handler, so the direct POST and the 404 fallback share one body. `isActive` is not made required, to avoid tightening the contract for existing callers (the repo has no schema validation layer — CLAUDE.md line 20).

### Environment notes (as-is)

- The dependency `autotask-node` (`npm:@wyre-technology/autotask-node`, GitHub Packages) cannot be installed on gcp-dev without a token. `src` does not import it (comments only); some tests call `jest.mock('autotask-node')`.
- Workaround: during install, temporarily removed that dependency and the lockfile, then restored `package.json` and `package-lock.json` with `git checkout`; placed a local stub package (with `.d.ts`) in `node_modules/autotask-node` so the mocks resolve. The stub lives only in `node_modules` (gitignored) and is **not committed**. Baseline and after ran in the same environment, so the results are comparable.
- Dependency versions came from a lockfile-less resolve and may differ slightly from the lockfile; a lockfile install in CI can confirm once more.

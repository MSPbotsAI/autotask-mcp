## 返工判断

**类型：开发错误（实现缺陷 + 测试缺口），不是需求变更。**

**依据**：QA 的 `[TEST · PRD-20317]` comment `90170265051691`（Minnie Zhou，2026-10-21），在 INT `autotask-mcp main@29d71f7`（含 `83091b7`，即 r1 的提交）上测试。结论：FAIL —— `includeUserDefinedFields: true` 时该调用在真实 Autotask API 上报错、不返回任何联系人，功能不可用；默认行为（flag 省略或 `false`）不受影响，通过。

**r1 错在哪**：`tool.handler.ts` 的 `autotask_search_contacts` 分支在 flag 开启时把 `includeFields` 设为 `[...SUMMARY_FIELDS.contacts, 'userDefinedFields']`，`AutotaskService.searchContacts()` 原样把它转发进 Autotask 查询的 `IncludeFields`。Autotask 拒绝 `IncludeFields` 里出现 `userDefinedFields` 这个值，返回 HTTP 500 `Unable to find userDefinedFields in the Contact Entity`。这正是 r1 技术设计在 Open Questions / Non-functional / Risks 里点名的风险（Autotask 的 `IncludeFields` 到底是 additive 还是 restrictive 当时没能确认，那个沙箱同样没法做现网验证——见 r1 的「Known local gap」）——但当时选的缓解办法（总是发送一个显式的超集）结果依然是错的，而且错的原因和当时设想的不一样：这个字段名本身就不是 `IncludeFields` 里的合法值，和 additive/restrictive 语义无关。

**本轮改了什么**：改的是 flag 这条查询构造路径所选的实现方式，不是产品需求本身。`docs/tickets/PRD-20317.md` 里的 AC1–AC6 与产品设计的「目标/非目标」不变，本轮仍以它为准——完整的产品设计与原技术设计叙述见该文档。只有 `searchContacts()` 被调用的具体方式变了（这属于 dev 自己的权限，见 `legs/dev.md` S1 / `references/docs-tree.md` 第 57 行附近的说明：只要不动用户可见行为，技术设计 dev 可以自行改）。

**现网验证**：这一棒依然没有做——本沙箱没有到 Autotask 的网络通路，也没有配置 Autotask 凭据（确认过：两处 `.env` 都没有 `AUTOTASK_*` 键）。如实记录而非编造，见下文 Self-test 的「Known local gap」。目前唯一的现网确认来自 QA 自己在 INT 上的测试（comment `90170265051691`），本轮的 mock 正是按照那次现网观察重写的。

### 技术设计更新（r2）

取代 r1「现有实现定位」/「改动清单」里关于 `tool.handler.ts` 的 `autotask_search_contacts` 分支、以及（因移除而受影响的）`src/services/autotask.service.ts` 的 `includeFields` 转发路径这一个调用点的记录：

- `src/handlers/tool.handler.ts`（`autotask_search_contacts` 分支，原在约 904-914 行，见 r1「现有实现定位」）：不再构造 `includeFields` 超集。仍然会在调用 service 前从 args 里剥离 `includeUserDefinedFields`，但现在无论 flag 是什么值，都调用 `s.searchContacts(rest)`，完全不带 `includeFields` 键。
- `src/services/autotask.service.ts` 的 `searchContacts()`（约 328-362 行）：**未改动**。它对 `options.includeFields?.length` 的判断现在对这个调用点来说是死代码（没有调用方再传它），但这段判断本身是通用的、无害的、有注释说明的——为了一次目标明确的修 bug 去删它属于范围外扩张，只会让 diff 变大却没有收益。仓库里没有其它调用点设置 `AutotaskQueryOptions.includeFields`（已用 `grep -rn includeFields src/` 确认）。
- `src/utils/response.formatter.ts`（`pickSummaryFields`/`formatCompactResponse`/`extraFields`）：**未改动，这正是关键点**——它本来就是对的。它读的是 Autotask 返回的**原始** item 上的 `userDefinedFields`（根据 QA 观察到的真实 API 行为，只要不发 `IncludeFields`，Autotask 默认就会带上所有字段），只在调用方的 `extraFields` 包含它时才把它拷进紧凑响应（这个门控挂在 `args.includeUserDefinedFields` 上，`tool.handler.ts` 共享的紧凑响应调用点这部分没有动）。这张单要的「按需开关」本来就一直发生在 formatter 这一层，不是 Autotask 查询这一层——r1 的错误是在查询层又多加了一道不必要且错误的门。
- `src/handlers/tool.handler.ts` 的 import 行（第 9 行）：移除了 `SUMMARY_FIELDS` 的导入——上面的改动之后这个文件里它没有任何剩余用法，而这个仓库的 `tsconfig.json` 开了 `noUnusedLocals: true`（不删会让 `tsc --noEmit` 报错）。`SUMMARY_FIELDS` 本身仍然从 `response.formatter.ts` 导出，供它自己的其它消费者使用。

综合效果：比 r1 更少的活动部件、完全相同的用户可见契约（AC1-AC6 不变），而那个会被 Autotask 拒绝的请求形状，现在从这个调用点结构上就不可能发出去了。

### 待报告人确认的问题（原样保留自 QA，dev 未自行解决）

**本轮未改动。** TC3 的文字和实现行为（原样透传 Autotask 返回的内容；formatter 不加修改地把 `userDefinedFields` 从原始 item 拷过去，不做任何过滤）完全保持 r1 定义的样子。这是一个潜在的「测试夹具/AC 与真实 Autotask 数据不一致」的问题（我们的夹具把一个无自定义字段的联系人建模成 `userDefinedFields: []`；如果真实 Autotask 实际返回的是「每个 UDF 都在、值为 null」的数组，TC3 在我们的夹具下依然通过，但夹具本身可能不代表现实）——按指示不自行猜测去改 TC3 或改行为来迁就它，而是留给报告人确认。本轮 TC3 的实际重跑结果见下文 Self-test「用例矩阵」。

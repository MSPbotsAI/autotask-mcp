## Requirement understanding

One line: Add support for returning contact custom fields from the Autotask MCP tool `autotask_search_contacts`, so downstream workflows can use those values directly from the same response without needing an extra lookup call.

The reporter (Felix.Zhou@mspbots.ai, filed 2026-10-12) wants `autotask_search_contacts` to include each matched contact's Autotask custom fields (user-defined fields) in the same tool response, so callers can act on that data without a follow-up lookup. The request is explicitly scoped to this one tool's response shape — not a broader redesign of the Autotask contact tooling. No workaround exists today. Reporter confirmed the solution preview "as-is" (ticket `text_content`, Solution Preview section).

## Current state (every claim carries path:line)

Code Project was empty on this ticket. No ticket text uniquely named a repo, so the `autotask_search_contacts` string itself was used to probe every repo resolvable from the `Code Project` field — zero hits everywhere except one repo not yet registered as a field option (see Blocked section). That repo, `https://github.com/MSPbotsAI/autotask-mcp` (checked out at `main` / `9700dde`), is an MCP server wrapping the Autotask REST API, one of a family of per-vendor `*-mcp` repos (`chargebee-mcp`, `bamboohr-mcp`, `halopsa-mcp`, etc.) that already are `Code Project` options.

Within that repo:

- `autotask_search_contacts` is declared in `src/handlers/tool.definitions.ts:311-331`. Its `inputSchema` has `searchTerm`, `companyID`, `isActive`, `page`, `pageSize` — no field-selection parameter of any kind.
- The handler (`src/handlers/tool.handler.ts:889-891`) calls `s.searchContacts(a)` and passes the raw args object straight through with no filtering.
- `searchContacts()` (`src/services/autotask.service.ts:328-358`) builds an Autotask filter and calls `http.query<AutotaskContact>('Contacts', filters, { maxRecords: pageSize })` — it never sets `opts.includeFields`. The underlying Autotask REST query only returns a contact's `userDefinedFields` when the caller explicitly lists it in the request's `IncludeFields` (`src/services/autotask-http.ts:390-404`, the `IncludeFields` pass-through). Since `searchContacts()` never asks for it, Autotask never returns it, independent of anything downstream.
- Even if it were returned by Autotask, the compact-response formatter would still drop it: `SUMMARY_FIELDS.contacts` (`src/utils/response.formatter.ts:27`) is a hardcoded allowlist `['id', 'firstName', 'lastName', 'emailAddress', 'companyID']`, and `pickSummaryFields()` (`src/utils/response.formatter.ts:34-55`) only copies those fields onto the response item (`autotask_search_contacts` is in `COMPACT_SEARCH_TOOLS`, `src/utils/response.formatter.ts:117`). There are two independent gates, not one.
- This is not an oversight unique to contacts — it is a documented, deliberate platform-wide decision. `CHANGELOG.md:661` (the `[1.0.4]` entry) records that `userDefinedFields` were removed from ticket search responses specifically to stop "result exceeds maximum length" errors. Any fix here has to stay opt-in rather than reverting that decision by default.
- `AutotaskContact` (`src/types/autotask.ts:23-33`) has no `userDefinedFields` field in its type, unlike `AutotaskTicket` (`src/types/autotask.ts:67`: `userDefinedFields?: AutotaskUserDefinedField[]`) — a typing gap only; the index signature `[key: string]: any` means it isn't a runtime blocker.
- Read/write asymmetry already exists for this exact entity: `autotask_update_contact` **already** accepts and forwards `userDefinedFields` (`{name, value}[]`) per `CHANGELOG.md:95` — "the handler already forwarded all args, so only the schema needed the addition." Only the search/read path is missing the capability the ticket asks for.
- `searchContacts()` types its options as `AutotaskQueryOptions` (`src/types/autotask.ts:671-680`), which has no `includeFields`. Most other search methods (`searchTickets`, `searchCompanies`, 20+ others, see `src/services/autotask.service.ts`) already use the richer `AutotaskQueryOptionsExtended` (`src/types/autotask.ts:683-698`), which **does** declare `includeFields?: string[]` — but nothing in `tool.definitions.ts` currently exposes `includeFields` as an MCP-facing parameter for any entity, so there is no existing end-to-end example of wiring a caller-supplied field list through to Autotask. This would be new wiring, not a copy of an existing one.
- The generic compact-response call site (`src/handlers/tool.handler.ts:1677-1684`) already has `args` in scope when it calls `formatCompactResponse(result, entityType, { page, pageSize })` — so a caller-supplied flag on `args` is reachable at the one place that currently strips custom fields back out.

## Blocked

**Blocker**: design could not continue past S0b (Code Project backfill). The repository is identified with code-level evidence (single, unambiguous hit — see Current state), but it is not yet an option on the `Code Project` field, and this is an unattended design tick with no browser session available to add one.

**Evidence**:
- `Code Project` field (id `7c16ef25-0109-4804-8824-88aeaca50311`, list `901716477471`) currently has 77 options, read live on 2026-10-12. None of them is `https://github.com/MSPbotsAI/autotask-mcp`.
- Two superficially similar legacy bare-name options exist on the field — `next-ticket-autotask` and `auto-task` — but neither resolves to a repository: `git ls-remote` returns "not found" for both names under both known hosts (`github.com/MSPbotsAI/` and `gitlab.mspbots.ai/mb-app-platform/`). They are not usable substitutes for `autotask-mcp`.
- The exact tool name `autotask_search_contacts` has zero hits in every one of the 24 repos currently resolvable from existing `Code Project` options (`app-workspace`, `mb-platform-agent`, `org-chart`, `mcp-service-gateway`, `app-ai-revops`, `mb-platform-webhook`, `mb-platform-channel`, `halopsa-mcp`, `mspbots-forms-mcp`, `mb-platform-openviking`, `mb-platform-agentos`, `mspbots-agent-mcp`, `chargebee-mcp`, `bamboohr-mcp`, `voipms-mcp`, `mb-platform-user`, `exchange_online_mcp`, `ms-graph-mcp`, `mb-platform-aegra`, `unifi-access-mcp`, `mb-platform-setting`, `aws-mcp`, `active-directory-mcp` (local clone, may be stale), `google-workspace-mcp`). The generic word "autotask" hits several of them (up to 472 times in `app-ai-revops`), but those are vendor-registry/documentation mentions, not the tool's implementation — confirmed by reading `mcp-service-gateway`'s hits, which are limited to README/vendor-onboarding docs about proxying Autotask credentials, not contact-search logic.
- `https://github.com/MSPbotsAI/autotask-mcp` exists, is reachable (`git ls-remote` succeeds), and does contain `autotask_search_contacts` at the three locations cited in Current state above.
- Writing a brand-new option onto this field through the ClickUp API is rejected with `403 FIELD_262` regardless of which field id is targeted — this is documented as a routing-layer rejection for personal tokens (`references/clickup.md`), not something specific to this field or this token's permissions. The only confirmed working path is a human with field-edit rights using the ClickUp UI picker (open the field, paste the full repo URL, click "Create" — this both adds the option and assigns it to the current ticket in the same action).
